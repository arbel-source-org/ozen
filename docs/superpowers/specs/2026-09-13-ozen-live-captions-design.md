# Ozen — live captions for hard-of-hearing conversation

## Problem

Grandmother has hearing loss, wears hearing aids, uses an iPhone. Existing live
transcription apps (evaluated: Nagish) are unreliable: inconsistent handling of
external microphones (a USB-C lavalier mic didn't work, AirPods worked but
inconsistently), no way to explicitly pick an audio input, and live
transcription is a minor feature bolted onto a bigger product rather than the
whole point. Family conversation is primarily in Hebrew.

## Who this is for

One family: grandmother (primary user, reads the screen), a handful of
relatives whose voices are worth naming once enrolled. Not building for the
App Store or a general audience — building for this specific household, kept
open source because there's no reason not to and someone else in the same
situation might find it.

## Hard requirements (from conversation with the owner)

- **Live, not batch.** Partial captions must update continuously as speech
  happens. A few hundred ms of lag to let a word stabilize is fine; several
  seconds of "record then transcribe" is not — it defeats the purpose.
- **Hebrew primary.** Whatever engine is used has to be genuinely good at
  Hebrew, not "supports 90 languages including Hebrew as an afterthought."
- **On-device.** Chosen specifically for latency (no network round trip) and
  because it means it keeps working with bad signal and doesn't leak family
  conversations to a third party.
- **Explicit input selection.** The single most concrete complaint about
  existing apps: they don't let you pick the microphone. Ozen must enumerate
  available inputs (built-in, AirPods/Bluetooth, wired/USB-C, MFi hearing-aid
  accessories) and let the user choose, and must handle mid-conversation route
  changes (AirPods reconnecting, a mic unplugging) without silently dropping
  audio or crashing.
- **Speaker detection.** Always-on diarization ("Speaker 1" / "Speaker 2" by
  default), with optional one-time voice enrollment so a cluster can be
  tagged with a real name ("Grandma", "Dana") going forward. Enrollment/naming
  can also happen after the fact by tagging an existing segment.
- **No visual overlap / clipped text.** Because this reads as accessibility
  software for someone who already struggles to follow conversation, a
  captioning UI that visually glitches (overlapping labels, truncated words)
  actively makes things worse, not just ugly.
- **Fully open source**, published under the owner's own GitHub account, with
  a small credit line in Settings ("Made by Arbel").

## Constraints

- No Mac available for development. Build/test loop:
  - Pure-Swift logic (no UIKit/AVFoundation/Speech import) lives in an SPM
    package and is unit-tested locally via the Swift toolchain installed on
    this Linux machine, and again in CI.
  - Anything touching Apple-only frameworks (AVFoundation, Speech, SwiftUI)
    is compiled and tested exclusively via GitHub Actions' macOS runners
    (free for a public repo), using `xcodebuild test` against the iOS
    Simulator.
  - Real hardware behavior — actual external mic switching, actual on-device
    model latency/battery, actual Hebrew transcription quality, actual
    speaker-ID accuracy in a real room — **cannot be verified by CI or by me**.
    That needs the owner (or the person building it) to install the app on a
    real iPhone and try it. This is called out explicitly rather than glossed
    over: "fully tested" for the parts CI can reach means real automated
    tests are green; for the parts CI can't reach it means a manual test
    checklist exists and has been run once on real hardware before calling a
    milestone done.
- Distribution starts as free Apple-ID sideloading (7-day reinstall cadence)
  per the owner's choice; the $99/year Apple Developer Program (unlocking
  TestFlight, no expiry) is adopted later only if the owner decides it's
  worth it once the app already works.

## Architecture

Two products in one repo:

```
Package.swift              <- SPM package: OzenKit (the testable core)
Sources/OzenKit/...
Tests/OzenKitTests/...
App/Ozen.xcodeproj (generated by XcodeGen from App/project.yml)
App/Ozen/...                <- SwiftUI app target, thin: wires OzenKit to screens
.github/workflows/ci.yml
```

`OzenKit` holds everything that can be designed as a protocol + pure logic,
so it's honestly unit-testable instead of only "testable in theory once you
have a simulator":

- `TranscriptionEngine` (protocol): `startStream()`, feed rolling audio
  buffers, yields a stream of `TranscriptToken` (partial or final, with
  timing). Two conformances:
  - `WhisperKitEngine` — wraps Argmax's WhisperKit (open-source, on-device
    Whisper via CoreML, actively maintained, already handles model
    management and streaming). Chosen over hand-wrapping whisper.cpp because
    it's Swift-native and purpose-built for exactly this.
  - `AppleSpeechEngine` — wraps `SFSpeechRecognizer` with
    `requiresOnDeviceRecognition = true`. Whether iOS actually ships an
    on-device Hebrew model varies by OS version and isn't something to
    assume — the engine checks `supportsOnDeviceRecognition` for `he-IL` at
    runtime and reports itself unavailable rather than silently falling back
    to server-based recognition (which would break the "on-device only"
    requirement without telling anyone).
  - Selected in Settings; both share one `TranscriptionEngine` interface so
    the rest of the app doesn't care which is active.
- `CaptionStabilizer` — pure logic, the answer to "won't words get cut off?".
  Takes a stream of partial/final tokens from the engine and produces a
  `TranscriptSegment` timeline where text is either "committed" (locked,
  never rewritten, safe to lay out permanently) or "pending" (may still
  change, rendered visually distinct — dimmer only, since Hebrew has no italic). A token commits when
  either the engine marks it final or a short silence gap has passed. Fully
  unit-testable with a fake token stream, no audio or UI involved.
- `SpeakerEmbedder` (protocol) + `EmbeddingClusterer` — diarization.
  - v1 embedder: classic MFCC-based spectral embedding via `Accelerate`
    (vDSP), computed per utterance. Not a deep model — that's a known,
    explicit v2 upgrade path (a CoreML speaker-embedding model swapped in
    behind the same protocol) — but it requires no training pipeline or
    model-conversion step to ship a first working version, and clustering
    quality can improve later without touching any caller.
  - Clusterer is embedding-agnostic online agglomerative clustering
    (cosine-similarity threshold, merges nearest cluster or opens a new one),
    unit-tested directly against synthetic embedding vectors — no audio
    needed to verify the clustering logic itself is correct.
  - Enrollment stores a named profile's centroid embedding; incoming
    clusters within threshold of a profile get that name instead of a
    generic number.
- `AudioInputManager` — thin wrapper around `AVAudioSession`:
  lists `availableInputs`, exposes the current route, and republishes on
  `routeChangeNotification` so the UI and the audio tap can react instead of
  silently going quiet (the exact bug pattern the owner hit with the lavalier
  mic).
- `AppSettings` — engine choice, language, selected input, enrolled
  speakers, credit string. `Codable`, persisted via `UserDefaults`/on-disk
  JSON (no need for anything heavier for a single-user app).

The `Ozen` app target is SwiftUI, `@Observable` view models per
`swiftui-patterns`, `@MainActor`-default per the Swift 6.2 approachable
concurrency model, with `@concurrent` reserved for the actual CPU-heavy step
(feeding audio into the transcription engine and running the embedder) so the
UI thread is never blocked by model inference.

### Screens

- **Live Caption** (the whole point): full-screen, large-type, high-contrast
  scrolling transcript. Each speaker gets a stable, distinguishable color
  swatch next to their turn (not decorative — it's the fastest way to follow
  who's talking without re-reading a name each time). A single persistent
  control row at the bottom: mic picker, pause/resume, engine indicator (small,
  not a badge-of-honor UI element). No modal dialogs interrupt an active
  conversation.
- **Speaker enrollment**: record ~30–60s, done from Settings or by tapping
  "who is this?" on an unlabeled segment in the transcript.
- **Settings**: engine choice (Whisper / Apple, with on-device-Hebrew
  availability shown honestly if Apple's isn't supported on that device),
  language, saved speaker profiles, and a small, quiet credit line reading
  "Made by Arbel" — not a splash screen, just a line in a list, consistent
  with the rest of the settings screen's tone.

### Visual direction

This is accessibility software for someone who already finds conversation
effortful, not a marketing surface — legibility beats personality. Concrete
choices: system font only (San Francisco already has correct Hebrew glyphs,
proper RTL shaping, and Dynamic Type support — a custom display face would
actively hurt an app whose primary user has impaired hearing, not vision, but
still benefits from the most legible/tested option available); a small fixed
set of high-contrast, colorblind-distinguishable speaker colors rather than
generated-per-speaker hues; dark background by default (a bright edge-to-edge
white caption screen is unpleasant to stare at during a whole conversation)
with light mode following system setting; no gradients, no card chrome, no
decorative iconography — every visual element on the Live Caption screen
earns its place by carrying information (speaker identity, commit state,
input source).

## Testing strategy

- `OzenKitTests` (pure Swift, runs both locally via `swift test` and in CI on
  Linux + macOS): `CaptionStabilizer`, `EmbeddingClusterer`, `AppSettings`
  encode/decode, `AudioInputManager`'s pure route-selection logic (given a
  fake list of inputs + a fake route-change event, is the right thing
  selected/reported).
- `OzenTests` (XCTest, macOS-runner-only via `xcodebuild test` against iOS
  Simulator): view model wiring, engine-availability reporting, settings
  persistence round-trip through the real app target.
- **Manual hardware checklist** (not automatable, tracked explicitly rather
  than silently skipped): install on a real iPhone; verify AirPods and at
  least one wired/USB-C mic are both selectable and both actually route
  audio; verify a mid-conversation route change doesn't drop the session;
  verify Hebrew transcription quality against a real conversation; verify
  two real family members enroll and get correctly told apart. Added
  2026-09-14, since the simulator has no haptics or real microphone: with
  captions running, each alert vibration (Settings → צלילים בבית → "איך כל
  התראה מרגישה", then a real doorbell or a keyword) is actually felt; with
  the phone face down on a table, the three-second alarm buzz does not
  raise a phone, alarm-clock, beep or knock alert of its own; the soft hum
  when someone starts talking after a quiet (on by default) doesn't garble
  the words captioned right after it on the phone's own microphone; a refused
  Bluetooth microphone leaves the picker's check mark on the one really
  recording; the white theme's status line and speaker names are easy to
  read in daylight.

## Explicit non-goals for v1

- No cloud fallback engine (contradicts the on-device/latency requirement;
  can revisit only if on-device Hebrew accuracy proves inadequate after
  real testing).
- No App Store submission, no multi-device sync, no account system.
- No deep-learned speaker-embedding model in v1 (tracked as a named upgrade
  path behind `SpeakerEmbedder`, not silently deferred).
